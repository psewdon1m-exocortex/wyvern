# Wyvern — план интеграции v0.2

Дата: 2026-09-19. Статус: принят, реализация исходного кода завершена. Документ сохраняет принятый план; фактическая реализация, проверки и отдельные условия выпуска перечислены в [журнале реализации](docs/IMPLEMENTATION.md).

Документ адаптирует [исходную спецификацию v0.1](wyvern-spec-v0.1.md) к Exocortex. Каноническое имя в коде, CLI, API и релизах — **Wyvern / wyvern**. Написание «wywern» из обсуждения не создаёт второй компонент.

## 1. Принятые изменения направления

| Решение владельца | Следствие для плана |
| --- | --- |
| Сервис с внешними LLM-вызовами устанавливает Wyvern либо использует установленный серверный экземпляр | Wyvern становится общей зависимостью хоста с install-or-reuse и отдельной регистрацией каждого потребителя |
| Главная сущность — Adapter, например Google adapter | Клиент выбирает полный настроенный профиль доступа к API; Route/Provider/Model перестают быть обязательными отдельными операторскими сущностями |
| Управление должно входить в общую TUI | Расширяется существующий `updater tui`; Wyvern предоставляет типизированный control API и CLI |
| Wyvern обновляется через Updater; отсутствующий Updater устанавливается | Самостоятельная установка Wyvern тоже начинает с ensure-Updater; обновления общие для всех его потребителей |
| Credentials обычно представлены одним API key | Основная форма подключения — один скрытый ключ; расширенная аутентификация только при требованиях конкретного driver |
| В Settings каждого LLM-сервиса нужна карточка Wyvern и выбор адаптера | Подключение и функциональные привязки доступны из сервиса; управление общими адаптерами — в TUI |

Сохраняются согласованные принципы: Kernel → Volt, изоляция ключей, целостная конфигурация, native Gemini для первых потребителей, нормализованный API, ограниченные attempts, Updater-owned deployment и отсутствие агентной логики в Wyvern.

## 2. Модель размещения и установки

По умолчанию на одном Linux-хосте работает один общий экземпляр Wyvern и один Updater. Первая установка LLM-сервиса создаёт отсутствующие компоненты; последующие установки добавляют потребителей к существующему экземпляру. Отдельный контейнер Wyvern у каждого приложения на одном хосте не создаётся.

Упаковка Wyvern — один непривилегированный контейнер с отдельным подписанным релизом, фиксированным systemd unit запуска Docker и runtime socket. Updater остаётся host daemon. Wyvern регистрируется как типизированный общий компонент, а не как принадлежащая первому потребителю часть его приложения.

### 2.1. Алгоритм install-or-reuse

1. Installer сервиса определяет зарегистрированный целевой экземпляр Wyvern. По умолчанию это локальный хост; явно настроенный удалённый экземпляр используется без автоматической установки второго.
2. Installer проверяет единственный локальный Updater. Если отсутствует — устанавливает проверенный подписанный релиз. Если установлен — проверяет совместимость и подключается. Совместимый существующий экземпляр не переустанавливается и не понижается в версии.
3. Через типизированную операцию Updater installer выполняет `ensure Wyvern`: обнаружение, проверка идентичности/версии/API, установка при отсутствии или подключение при совместимости.
4. Проверка и установка защищены общей блокировкой хоста и idempotency key. Две одновременные установки не создают второй daemon, контейнер или набор управляющих credentials.
5. Потребитель получает отдельную идентичность и ограниченный доступ к Wyvern. Локальный реестр Updater фиксирует зависимость установленного сервиса от общего компонента.
6. Проверяются процесс, control API и конфигурация. Отсутствие настроенного адаптера отображается как ожидание настройки LLM, отдельно от ошибки установки компонента.
7. После выбора адаптера проверяется готовность LLM-функции. Пока адаптер не выбран или не готов, сервис не сообщает, что LLM-подключение работает.

Самостоятельный bootstrap Wyvern выполняет тот же порядок: обеспечить Updater → поручить ему установку Wyvern. Запущенный runtime Wyvern не скачивает Updater и не получает root/Docker socket. Уже установленный Wyvern с отсутствующим Updater восстанавливает эту зависимость через installer/repair, а не через generation API.

Если найден несовместимый Wyvern/Updater, операция показывает требуемую совместимость и путь проверенного обновления. Нельзя молча устанавливать вторую копию, откатывать более новую версию или ломать других потребителей. Поддерживаемые диапазоны API, минимальная версия и проверенные версии зависимостей входят в release contract.

Явно выбранный удалённый Wyvern не заменяется локальным при сетевом сбое. Изменение размещения — отдельное действие. Локальная TUI управляет экземпляром своего хоста; удалённый экземпляр обновляет Updater на его хосте. Поддержку полноценного удалённого enrollment можно выпустить после локального install-or-reuse, сохранив это различие в схеме подключения.

### 2.2. Жизненный цикл общей зависимости

- Удаление приложения удаляет только его регистрацию и доступ. Общий Wyvern, адаптеры и другие потребители сохраняются.
- Отключение одного потребителя не выполняет global drain и не выключает Adapter.
- Обновление Wyvern учитывает всех зарегистрированных потребителей, их требования к API и активные запросы.
- Общие настройки и credentials не принадлежат первому установившему сервису.
- При поломке существующей установки предлагается repair; обнаружение «уже установлен» не считается доказательством здоровья.
- Runtime state и health разграничивают `installed`, `reachable`, `configuration_loaded`, `client_linked`, `adapter_selected` и `llm_ready`.

## 3. Adapter как основной контракт

**Adapter** — именованный, полностью настроенный профиль подключения к внешнему или локальному LLM API. Например, `google-main`: Google API, адрес, credential, выбранные модели, capabilities, ограничения и правила выполнения.

**Driver** — программная реализация протокола (`google`, `openai-compatible` и последующие). Driver выполняет HTTP, перевод запроса, обработку файлов/streaming, извлечение usage и нормализацию ошибок. Установка Adapter из TUI создаёт конфигурацию уже поставленного driver; произвольный код из внешнего источника при этом не загружается.

Несколько Adapter могут использовать один Driver: например, разные Google API keys, проекты, квоты или настройки обработки данных. Смена driver у действующего Adapter требует проверки совместимости привязанных функций.

Состав Adapter:

- стабильный `adapter_id`, отображаемое имя, `driver`, состояние enabled/disabled;
- endpoint: проверенный default из driver либо разрешённое операторское значение;
- схема аутентификации и ссылка на credential в Volt через Register;
- профиль моделей: default и при необходимости логические `text`, `media` и другие;
- capabilities и проверяемые ограничения каждого профиля;
- defaults генерации, concurrency, deadlines, retries и политика передачи содержимого;
- разрешения на использование и сведения о текущем поколении конфигурации.

Provider/Model/Policy могут оставаться внутренними структурами реализации. Начальный интерфейс не требует отдельно заводить Provider, Model, Route и Policy, чтобы добавить один API key.

Клиентский вызов концептуально выглядит так:

```json
{
  "adapter_id": "google-main",
  "profile": "text",
  "messages": [{"role": "user", "content": "..."}],
  "response_format": {"type": "json_schema", "schema": {}},
  "metadata": {"operation_id": "..."}
}
```

Это пример направления схемы, не опубликованный API. `profile` можно опустить для default. Caller не передаёт provider endpoint, API key или произвольное remote model name. Аутентифицированная идентичность определяет разрешённые Adapter; поле `adapter_id` само по себе не даёт доступ.

Прежняя Route-first модель не является основным пользовательским контрактом. При необходимости логические маршруты реализуются как внутренние профили/алиасы внутри Adapter. Fallback на другой Adapter разрешается только явной политикой; выбор Google adapter не должен незаметно отправлять данные другому провайдеру.

Ответ содержит `request_id`, Adapter, профиль, фактически выбранную модель, поколение конфигурации, finish reason, usage и attempts. Эти данные используются для диагностики и provenance, без provider credentials и чувствительных HTTP-деталей.

## 4. Credentials и целостная конфигурация

### 4.1. Простое подключение API

Основная форма создания Google adapter: имя → driver Google → API key → модель/профили → проверка и публикация. Endpoint и схема заголовков имеют проверенные defaults. Дополнительные поля появляются только если их требует driver: например, project ID или другой тип credential.

API key — непрозрачная строка. Передача через masked input или stdin; ключ не входит в URL, argv, историю TUI, журнал, persistent job payload, клиентскую карточку или обычный JSON status. TUI показывает наличие ключа и его версию, а не само значение. Замена ключа — write-only действие.

Ключ сохраняется в Volt и разрешается через Kernel. Размер одного ключа не требует универсального OAuth/workflow engine; достаточно типизированной схемы credentials драйвера. В списке Adapter нельзя выводить ключ или его часть для различения записей — для этого есть имя и ID.

### 4.2. Владение данными

| Данные | Владелец |
| --- | --- |
| Значения Adapter и credentials | Volt |
| Ссылки, опубликованные bindings и метаданные конфигурации | Kernel / Register |
| Разрешённый immutable runtime snapshot | Wyvern, только память |
| Выбор Adapter для функции конкретного экземпляра сервиса | Его scoped binding в Kernel/Volt |
| Установленные версии, runtime paths и список локальных потребителей | Host registry Updater |
| Текущий экран, незавершённая форма | TUI / браузер, без authoritative конфигурации |
| Задания, prompts, история и конечные результаты | Сервис-потребитель |

Bindings адресуются по instance/client/function, чтобы два экземпляра одного сервиса не перезаписывали выбор друг друга. Локальная БД приложения может хранить историю и кэш наблюдений; она не становится вторым источником выбранного Adapter. Новое значение применяется после подтверждённой публикации binding.

Для MVP конфигурация Adapter может публиковаться ограниченным JSON bundle через Volt. Credentials — отдельные ссылки. Одна запись/поле существенно упрощает начальный комплект; нельзя встраивать ключ в обычный экспортируемый JSON конфигурации.

### 4.3. Reload и rollback

Учитываются Register revision, версии значений Volt и поколение конфигурации Wyvern. Проверка только ETag Register недостаточна: обновление существующего API key в Volt должно обнаруживаться даже при неизменной ссылке.

Публикация: подготовить значения → проверить ожидаемые версии всех зависимостей → проверить конфигурацию Wyvern → атомарно опубликовать комплект с optimistic concurrency. Новый snapshot активируется целиком; текущие запросы завершаются с прежним. Агрегированный hash ревизий служит идентификатором, но сам по себе не обеспечивает согласованность чтений между пакетами.

Kernel/Volt нужно расширить для согласованного чтения закреплённых/ожидаемых версий и ограниченной публикации. Не требуется распределённая транзакция установки сервиса и редактирования всех записей хранилищ. Ошибка подготовки оставляет текущую конфигурацию активной; незавершённый кандидат виден как неподтверждённый.

Rollback касается только выбранного Adapter/binding/комплекта Wyvern и создаёт новую публикацию. Глобальная ревизия Register остальных сервисов не откатывается. Отозванные credentials не восстанавливаются автоматически вместе со старой конфигурацией.

При недоступности Kernel или Volt работающий Wyvern продолжает работу на последнем разрешённом снимке. Cold start требует обоих источников. Для отзыва доступа отдельно задаётся срок допустимой устарелости auth-снимка; бессрочный last-known-good не означает бессрочный доступ отозванного клиента.

## 5. Доступ и границы управления

Изоляция ключей требует отдельных сервисных identities и ограничений разрешения Register keys. Нынешний общий Kernel service token позволяет читать любые опубликованные значения; он не должен сохранять возможность получать provider keys или credentials других потребителей после миграции.

- Wyvern runtime читает собственную конфигурацию и provider credentials.
- Потребитель читает свой binding/доступ, получает каталог только разрешённых ему Adapter и изменяет только собственные функциональные привязки.
- У каждого потребителя отдельный credential к Wyvern; нельзя использовать общий Kernel token как достоверный `client_id`.
- Операторская публикация Adapter и secrets использует отдельные ограниченные полномочия. Runtime principal Wyvern не получает общий write-доступ в Kernel/Volt.
- Старые Register aliases, открывающие тот же provider key, удаляются из доступного клиентам набора; миграция завершается ротацией.

Изначально достаточно отдельных bearer tokens и TLS для сетевого доступа. Локальные UDS дополняются файловыми правами и сервисной аутентификацией. Масштабная PKI, tenant IAM и сложная модель ролей не являются условием MVP.

## 6. Общая TUI и CLI

Интеграция строится на существующем [контракте Updater TUI](../updater/docs/TUI.md). В текущей локальной реализации Wyvern уже присутствует в списке, но имеет статус planned; операторские действия разрешены только для Updater, Neptune и Gryphon.

В `sudo updater tui` раздел Wyvern должен предоставлять:

1. Установку/подключение/repair и статус экземпляра текущего хоста.
2. Установленную версию, проверку релиза, обновление, drain и восстановление после ошибки.
3. Каталог Adapter: создать, проверить, изменить, выключить, заменить API key.
4. Просмотр подключённых сервисов и их функциональных bindings.
5. Состояния Kernel/Volt, активную конфигурацию, запросы и ограниченную телеметрию.
6. Историю операций, результат последнего действия и reconnect по durable job ID.

CLI Wyvern предоставляет те же типизированные операции в machine-readable JSON и диагностику при недоступной TUI. Отдельный Wyvern Web UI не создаётся. Формулировка «CLI only» в исходной спецификации заменяется на «общая TUI + CLI + service Settings integration».

### 6.1. Разделение полномочий

TUI использует root-only operator socket Updater, отдельный от service-mounted socket. Root facade может вызвать только известные административные операции Wyvern и ограниченный конфигурационный publisher. Updater отвечает за install/update/repair; проверку Adapter выполняет Wyvern; постоянные данные публикуются через Kernel/Volt.

Browser backend потребителя использует свой service socket/token и узкие binding-операции. Он не получает root operator socket, Wyvern admin socket, произвольную команду или возможность управлять чужими Adapter.

Операторский путь публикации должен быть реализован вместе с созданием Adapter в TUI. Недопустимо показывать кнопку Save без рабочего, авторизованного способа сохранить ключ в Volt и ссылки в Kernel. Credentials существуют в форме и передаче только транзитно; после потери процесса job не восстанавливает ключ из журнала, а сообщает о необходимости повторного ввода.

### 6.2. Требования к терминалу

Сохраняются arrows/Enter/Esc/Tab, monochrome mode, обычный SSH PTY, masked input, безопасный bracketed paste, очистка управляющих последовательностей из внешнего текста, сохранение формы при resize и восстановление терминала при выходе. Для переносимого управления API/CLI не используются размер пикселей, web-fonts или специальные шрифты терминала.

Закрытие TUI/SSH не отменяет принятую установку или обновление. Повторное подключение читает job по ID. Реальный платный тест вызова модели отделён от проверки схемы/доступности и требует явного запуска с показом целевого Adapter; автоматическая установка и выбор Adapter не выполняют генерации.

## 7. Карточка Wyvern в Settings потребителя

Карточка обязательна для каждого сервиса, имеющего внешние LLM-функции. Первые потребители — Mastermind и Laboratory. Используется общий Settings card pattern Parts 01/10 с допустимой темой конкретного сервиса.

Состав карточки:

- экземпляр Wyvern: идентичность, локальное/удалённое подключение, версия;
- состояние соединения и время последней успешной проверки;
- связанный service/client identity без token;
- основной выбор Adapter из доступного этому сервису каталога;
- при нескольких LLM-функциях — дополнительные bindings по функциям, например текст и медиа Crusher;
- поддерживаемые capabilities, причина несовместимости или неготовности выбора;
- действия подключить/проверить/применить выбор/отключить текущий сервис;
- состояние выполняемой операции и стабильный job/request ID.

Обычный случай — один Adapter. Несколько bindings не должны заставлять оператора проходить сложную настройку, если один Google adapter покрывает все функции. Выбор remote model и ввод provider API key выполняются в настройках Adapter через TUI, а не дублируются в каждой карточке.

| Состояние | Поведение карточки |
| --- | --- |
| Компонент отсутствует на старой установке | Install/connect через ограниченную операцию локального Updater; это recovery-путь, при новой установке ensure выполнен автоматически |
| Updater отсутствует | Указание installer/host TUI repair; web-процесс не повышает себе привилегии |
| Wyvern установлен, клиент не зарегистрирован | Connect/register own service |
| Клиент связан, Adapter не выбран | Доступный список и Apply; LLM-функция ожидает настройки |
| Adapter несовместим | Причина, какие функции не поддерживаются, выбор совместимого Adapter |
| Соединение готово | Выбранный Adapter, готовые функции, Check connection |
| Сеть недоступна | Offline / last seen; выбранный binding сохраняется |
| Установка/обновление выполняется | Текущая стадия, ID, reconnect; принятие запроса не равно успеху |
| Доступ отозван или Adapter выключен | Явная недоступность функции; без скрытого переключения на другой провайдер |

Backend проверяет capabilities и права до публикации нового binding; CAS конфликт не перезаписывает другой выбор. Активные запросы завершаются по старому снимку, новые используют опубликованный binding. Отключение одного сервиса не удаляет общий Adapter.

Карточка показывает обновление общего компонента, но изменение версии проходит через авторизованный host-level workflow с указанием затрагиваемых потребителей. Право менять свой binding не даёт права произвольно обновлять или останавливать общий экземпляр.

## 8. API, медиа и execution policy

Первые реальные сценарии требуют native Google driver, JSON Schema, usage, подсчёта токенов, текста и затем PDF/аудио/видео. OpenAI-compatible driver и tool calls следуют за покрытием текущих потребителей. Схема streaming проектируется сразу; end-to-end SSE и cancellation входят в базовую реализацию шлюза.

Data plane должен включать generation, доступный клиенту каталог Adapter/capabilities, ограниченный token-count/estimate и краткоживущие media handles. Финальные paths/schemas фиксируются отдельным API contract до реализации клиентов.

Выбор Adapter не разрешает произвольный URL. Медиа загружается через ограниченный канал, имеет владельца, MIME/размер/срок жизни. Provider upload URI скрыт за Wyvern handle. Для гарантированной очистки после restart потребуется ограниченный журнал технических media metadata; иначе контракт честно ограничивает восстановление и использует provider expiry. Тела файлов/диалогов не становятся authoritative хранилищем Wyvern.

Извлечение документов, чтение Saturn через Neptune, prompts, локальные embeddings, задания и запись результатов остаются в Mastermind/Laboratory. Подсчёт токенов и лимиты проверяются для фактической модели, включая повторную проверку при fallback. Provider-specific options сохраняются в Adapter, не становятся произвольным passthrough API.

На этапе миграции по умолчанию одна provider attempt на запрос; существующие очереди потребителей сохраняют свои ограниченные повторы. Следующий этап добавляет согласованный общий бюджет попыток/deadline, чтобы retries клиента, gateway и SDK не умножались. После начала содержательного streaming повтор/fallback запрещён.

Отмена, неоднозначный исход provider call, утраченный media handle и deadline имеют явные ошибки. Гарантия однократного commit результата остаётся у потребителя; единственный billable request при сетевом сбое не обещается.

Лимиты размера, конкурентности, очередей, attempts и времени обязательны сразу. Usage/cost сначала диагностические, с явным unknown для отсутствующих данных. Жёсткие долговечные бюджеты и общий лимит между несколькими хостами требуют отдельного учёта; локальные счётчики Wyvern не выдаются за глобальную квоту API key.

## 9. Updater, обновление и восстановление

Wyvern выпускается независимо; релиз не собирает соседние checkout. Проверяются подпись manifest, digest образа/bundle, API/config compatibility и точная выбранная версия. TUI и installer используют один typed component lifecycle.

Обновление: preflight всех потребителей и схемы → загрузка/проверка артефакта → drain → ограниченное ожидание запросов/медиа → замена образа → проверка версии и конфигурации → снятие drain → финальная readiness. Ошибка до замены сохраняет рабочий процесс; последующая ошибка запускает ограниченный rollback. Нужен cleanup drain при отмене/неудаче до остановки, чтобы старый экземпляр не остался навсегда закрыт для запросов.

Drain управляется самим Wyvern. Updater использует отдельную readiness/preflight диагностику во время maintenance: `ready=false` в drain не является ошибкой liveness. После восстановления обслуживания проверяется именно data-plane readiness. Liveness не зависит от платной генерации или текущего здоровья внешнего провайдера.

Предлагается отдельный профиль общего компонента с внешним authoritative config. Он не получает фиктивный application backup и не обходит нынешнее требование ZIP произвольным полем запроса. Расширение backup/update contract фиксируется в центральной документации и доверенном component profile до реализации. Для схемной миграции обязательна проверенная восстановимость соответствующих данных Kernel/Volt; миграция не выполняется неявно на startup.

В собственный backup Wyvern не включаются provider keys, кэш разрешённых значений или `.env`. Если появляются authoritative журналы лимитов или cleanup state, их recovery semantics описываются отдельно. Копирование всей конфигурации Kernel в Wyvern ради offline cold start не вводится.

Разные хосты имеют независимые Updater и Wyvern. Один local update не обновляет всю систему; одинаковый Adapter/API key на нескольких хостах требует осознанного распределения лимитов.

## 10. Карта изменений существующих компонентов

| Компонент | Работа |
| --- | --- |
| Wyvern | Runtime, Adapter/Driver, snapshots, generation/media/SSE, scoped catalog/bindings, control API, CLI, packaging и tests |
| Kernel | Service identities/grants, согласованное resolve, scoped publication/binding update, расширение Register profile, аудит без значений |
| Volt | Формат хранения Adapter/keys, версия-зависимое чтение/публикация, ротация; простой API key остаётся обычным secret field |
| Updater component layer | Declare consumers, install-or-reuse, registry/lifecycle/repair/update, locks, compatibility всех клиентов, cleanup/rollback |
| Updater operator API / TUI | Снять planned-only состояние Wyvern, добавить typed actions, формы Adapter, scopes, health и durable jobs |
| Installers Mastermind/Laboratory | Автоматический ensure-Updater/ensure-Wyvern и регистрация собственного экземпляра сервиса |
| Settings Mastermind/Laboratory | Карточка Wyvern, доступный каталог, capability validation, scoped Apply/Disconnect, состояния и reconnect |
| LLM-клиенты Mastermind/Laboratory | Adapter-first вызовы, медиа/token-count/usage, сохранение provenance и собственных очередей |
| Nginx / release CI | Локальные upstreams, при необходимости TLS/SSE, отдельные signed artifacts и compatibility evidence |
| Центральная документация | Parts 01/04/05/07/09/10 и профиль deployment: новый общий компонент, TUI/Settings, scopes, installation/recovery |

При первичном анализе профиль Kernel отклонял дополнительные keys. Текущая база уже сохраняет дополнительные записи Register; это подтверждено её тестами. Для Wyvern реализован отдельный versioned validator конфигурации и точные grants на разрешаемые ключи, без изменения обязательных ключей исходного профиля.

Neptune, Saturn, Perimetr и Agent не получают новые LLM-зависимости автоматически. Изменения нужны только если конкретный сервис добавляет внешние LLM-функции или отдельный recovery contract потребует интеграции. Существующие локальные неопубликованные integration patches Mastermind учитываются отдельно от доступных релизов.

## 11. Последовательность реализации и приёмка

### Этап 1. Зафиксировать контракты

Обновить спецификацию под Adapter/Driver/ClientBinding, schemas и identity, state vocabulary, service dependency manifest, Kernel/Volt publication, общий компонент Updater и карточку/TUI. Согласованные в этом документе решения перенести в применимые Parts и будущие repo-local policy locks; не оставлять конфликтующие активные инструкции.

Результат: versioned контракты и проверяемые consumer requirements для текста/PDF/медиа Mastermind и Laboratory. Текущая параллельная TUI-разработка остаётся исходной базой; её изменения не перезаписываются.

### Этап 2. Установка, состояние и доступ

Скелет Wyvern, health/control CLI, bounded snapshots, сервисная идентификация; типизированный lifecycle Updater. Проверить standalone Wyvern без Updater, новый LLM-сервис на пустом хосте, повторную и конкурентную установку, reuse здорового экземпляра, несовместимость и repair. На этом этапе допустим статус Adapter not configured, но не ложная LLM readiness.

### Этап 3. Adapter и общая TUI

Google driver, простой API-key flow, безопасная публикация Adapter в Kernel/Volt, каталог и diagnostics, TUI CRUD/rotation. Проверить свежесть ключа при неизменной Register revision, атомарный reload, invalid candidate и scoped rollback. Ключ не обнаруживается в TUI output, CLI, логах, job state или конфигурационном export.

### Этап 4. Settings и текстовые потребители

Карточки обоих сервисов, scoped binding, native Google generation, JSON Schema, token count, usage/provenance, SSE/cancellation. Перевести текстовые сценарии. Проверить, что сервис видит только разрешённые Adapter, не меняет чужие bindings и не получает provider key. Изменение выбора не требует переустановки сервиса.

### Этап 5. Медиа и полная миграция

PDF/изображения/аудио/видео/YouTube в пределах возможностей Google driver и существующих требований. Проверить lifecycle upload/wait/use/delete, crash/expiry, ограничения данных и отсутствие доступа Wyvern к полному Vault/Saturn. Удалить provider transport и ключи из мигрированных клиентов, закрыть старые secret aliases, выполнить ротацию. Только после этого объявлять полную миграцию текущих потребителей.

### Этап 6. Обновления и эксплуатационная готовность

Проверить update/rollback общего Wyvern с двумя клиентами, streaming и активным media request; падение TUI/SSH, restart Updater и reconnect; конфигурационную совместимость старого бинарника; ограниченность памяти/телеметрии. Отключение или удаление одного потребителя не нарушает другого. Отсутствие Wyvern приостанавливает LLM-функции и сохраняет работу остальных функций приложений.

После базовой приёмки: дополнительные drivers, tool calls, согласованные retries/fallback, улучшение usage и при необходимости долговечные/межхостовые бюджеты. Приоритет — реальные потребители; multi-tenant SaaS и универсальный agent runtime не входят в задачу.
